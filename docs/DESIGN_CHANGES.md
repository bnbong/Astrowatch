# 개발 과정과 설계 변경

> 기획 검증(명세 2.7)과 실제 실행에서 드러난 사실에 따라 설계를 바꾼 기록. 갱신일 2026-11-20.

| 발견 | 설계 변경 |
|---|---|
| 12/14 유성우는 예보 범위 밖이라 "충족"이 성립할 수 없다 | 판정을 충족, 조건부 충족, 불충족 3단계로 |
| 카카오로 지오코딩하면 카카오 키 누락 시 날씨와 박명까지 실패한다 | 지역 표를 로컬에 두고 출몰 API는 위경도 버전 사용 |
| 개발 네트워크에서 Open-Meteo 차단, 카카오 반경 20km 상한 | 백업 예보를 기상청 중기예보와 OpenWeatherMap으로, 반경 20km 고정 |
| "안드로메다 은하 보기 좋은 날짜"가 되묻기만 반복 | 날짜 없음은 되묻지 않고 기본 범위를 쓰고 그 사실을 밝힌다 |
| 은하는 천문현상 목록에 없어 엉뚱한 유성우를 추천 | 천체 카탈로그와 고도 계산으로 "떠 있는 시간"만 창으로, 달이 진 뒤 구간으로 자른다 |
| "화성 제일 잘 보이는 시간대"에 키워드 규칙이 틀린 Tool을 고른다 | 사실 질문의 Tool 선택을 LLM 판단으로 바꾸고 판단 이유를 이벤트에 기록 |
| LLM이 지나가듯 말한 지역과 현상까지 "고정"으로 묶어 재계획이 1회 만에 끝난다 | 고정은 명시적 표현만, 단일 날짜만 자동 고정 |
| 후속 요청의 답변이 "바꿀 부분이 없다"고 설명한다 | 이전 조건과의 차이를 응답 단계에 넘겨 바뀐 항목을 먼저 말하게 |
| GMS의 OpenAI 경로가 마지막 날 사용 불가 | 공급자 설정 하나로 Anthropic 호환 경로(`claude-haiku-5-5`)로 전환 |

**3일차 오후 (2026-11-20, 심화 F3020, F3021, F3022 와 하늘 가리키기 추가 중)**

| 발견 | 설계 변경 |
|---|---|
| 위키백과 문서를 한 건씩 받으면 429(요청 제한)가 난다 | 제목 확인은 50개씩, 도입부(`exintro`)는 20개씩 묶어 받고, 429 는 `Retry-After`(없으면 15~120초) 뒤 재시도, 받은 본문은 `data/cache` 에 남겨 이어받기 (`rag/collect.py`) |
| 로컬 영어 임베딩(all-MiniLM-L6-v2)은 관련 없는 한국어 문장끼리도 유사도가 0.6 안팎이라 최소 점수 0.6 으로는 걸러지지 않는다 | 최소 점수를 공급자별로: local 0.75, 그 밖 0.35. 천체, 용어 이름이 맞는 문서는 이름 가산으로 살린다 (`rag/search.py`) |
| 재계획 상한에 닿은 턴(R2, R3 mock)도 로깅 Agent 가 이상으로 본다 | 의도한 동작으로 둔다: `limit_reached=true` 인 `replan` 은 `excessive_replan`. verify 는 그 턴에 한 번만 재구성하고, Worker 는 캐시만 써서 Tool 호출이 늘지 않는다 (AGENT_DESIGN 8-2) |
| 계획에 가리킬 천체를 새 열 `plans.target_object` 로 두자, 사용자가 일부러 비운 값까지 다시 채워질 수 있었다 | 기존 계획의 제목 추론 백필을 DB 당 한 번만 실행하고 `PRAGMA user_version` 으로 표시 (`storage/plans.py`) |
| 하늘 가리키기는 휴대폰의 현재 위치(Geolocation)가 필요하다 | 보안 헤더 `Permissions-Policy` 를 `geolocation=(self)` 로: 같은 출처에서만 위치 허용, 카메라, 마이크는 차단 유지 (`app/security.py`) |

개발은 Claude(설계와 계약, 오케스트레이션) → Opus 에이전트(모듈 구현) → Codex(코드 리뷰와 실제 E2E) 순환으로 진행했고, 공통 응답 봉투, 스키마, State, 이벤트, DB 계약을 먼저 고정한 뒤 모듈을 병렬로 구현했습니다.
