# Codex 리뷰: 심화 기능 (F3020 감사, F3021 Planner/Worker, 하늘 가리키기)

> 2026-11-20 12:20, codex exec (gpt-6-astra, read-only sandbox). 지적 6건은 같은 날 수정했다(수정 내역은 docs/VERIFICATION.md 8절).

**6건의 수정 필요 사항을 확인했습니다.** 가장 중요한 문제는 Worker가 고정된 관측 날짜와 다른 날짜의 예보를 원래 날짜의 결과로 사용할 수 있다는 점입니다.

파일은 수정하지 않았고, 네트워크·API 키를 사용하는 실행은 하지 않았습니다. 지정한 pytest 명령은 읽기 전용 환경에서 임시 디렉터리를 만들지 못해 **수집 전에 실패**했습니다. 별도로 파일 쓰기가 없는 천체·프런트 수학 테스트 함수 15개를 직접 호출했고 모두 통과했습니다. 아래의 “테스트 있음”은 전체 pytest 통과를 의미하지 않습니다.

**교차 기능 통합**

- **계획 외 호출:** `planner_tasks`가 있으면 이를 우선하고, 없으면 classic의 `plan stage_end.planned_tools`를 사용합니다(`audit.py:134`). Tool 이름만 비교하므로 **같은 Tool의 인자 수정 retry는 UNPLANNED_CALL로 판정되지 않습니다.** 다만 Worker 실행 이벤트를 실제 감사에 연결하는 전용 테스트는 없습니다.
- **재계획 중복 계산:** 감사 재구성 자체는 `REPLAN`을 발행하거나 `replan_count`를 올리지 않습니다. 기존 상한 도달 경로에서 무한 루프·이중 집계 문제는 발견하지 못했습니다.
- **응답과 저장된 턴:** 응답에 audit와 `llm_calls`를 붙인 뒤 저장된 턴을 갱신합니다(`service.py:201`). 일치 검사도 있습니다(`test_planner_worker.py:104`). 다만 갱신은 별도 저장 단계이고 오류를 삼키므로 **갱신 실패 시에는 반환 응답과 저장된 턴이 달라질 수 있습니다**(`service.py:347`). 실패 경로의 일치 보장은 없습니다.
- **LLM 계측:** `llm_calls`는 문서화된 **판단 이벤트 수**입니다. structured-output fallback에서 발생하는 개별 모델 요청 횟수나 응답 생성 호출까지 포함하는 비용 계측값으로 해석하면 안 됩니다.

**추가 테스트 제안**

1. **고정 날짜 예보 retry:** 다른 날짜의 성공 응답을 제안해도 거절하고, 원래 날짜의 캐시에 저장되지 않는지 검사.
2. **필수 작업 실패 전달:** 박명·예보의 미해결 오류, 잘못된 retry, LLM 예외 후 Planner가 task ID와 실패 이유를 받는지 검사.
3. **Worker→audit 통합:** 수정 인자 retry가 NORMAL이고, 실제 계획 외 Tool은 ANOMALY인지 검사.
4. **비동기 포인터:** 지연 응답으로 `refreshMoving()`과 대상 선택을 교차 실행하고 대상 이름·key·좌표가 항상 같은 대상을 나타내는지 검사.
5. **천문·센서 경계:** 달의 이동 좌표를 반영한 출현 시각, datetime 양끝, nonzero gamma, 화면 회전 ±90°/180°, 실제 iOS 이벤트 처리의 결합 테스트.
6. **백필·저장 복구:** 구버전 DB 마이그레이션, 두 번째 프로세스 시작, 명시적 null 유지, 백필 중 예외와 재시도, 감사 후 턴 갱신 실패 테스트.
7. **보안 회귀:** 감사 재실행의 호출 제한 및 악성 제목·진단·검색 결과 문자열을 DOM에 렌더링해 실제 요소나 속성으로 해석되지 않는지 검사.
